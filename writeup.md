# Fuzzer

## Architecture Overview

Our tooling targets the binaries delivered with the assignment. The workflow is split into two cooperating components:

- `fuzzer.py` orchestrates corpus management, mutation scheduling, coverage bookkeeping, and crash triage.
- `forkserver.py` (the “somethingawesome” bonus feature) supplies a persistent forkserver that keeps the target binary mapped in memory, allowing each fuzz iteration to start from an identical process snapshot with near-zero start-up cost.

Each iteration starts from a seed input (the example fixtures or previously discovered interesting cases), applies one mutation strategy, and then executes the target through the forkserver. A per-run timeout prevents hangs from stalling the campaign. Execution metadata (exit status, signal, runtime, coarse coverage hash) is recorded to drive queue prioritisation. Crashes and hangs are appended to `fuzzer_output/bad_<prog>.txt` with metadata for offline analysis.

The fuzzer operates in two phases:

1. **Deterministic warm-up.** Structured payloads exercise known weak spots such as format strings and XML recursion depth. These inputs are generated by dedicated builders inside `XMLMutator`.
2. **Coverage-guided exploration.** Randomised mutations are selected by weight. When a mutated input increases the (approximate) coverage map, it is promoted into the interesting input queue to seed future mutations.

Before fuzzing a binary, `utils.detect_format` detects the type of the input file using the `libmagic-based Magic` library. Based on the detected type (eg JSON, XML, CSV, JPEG, ELF, PDF, or plain text), a corresponding mutator is selected: `JSONMutator`, `CSVMutator`, `XMLMutator`, `JPEGMutator`, or the plain-text stack (`BaseMutator` with help from `OctetMutator` for binary-heavy inputs). Different mutation strategies are applied to the example input before it is fed into the target binary. The corpus queue starts with the seed plus deterministic expansions; the random stage samples from that growing queue so newly discovered behaviours quickly gain mutation budget.

## Mutation Strategies

Each input family receives a dedicated mutator layered on top of the shared byte-level havoc stage:

- **XML inputs (`XMLMutator`).** Deterministic builders such as `_inject_many_children()` and `_deeply_nested_nodes()` synthesize thousands of sibling nodes and 1,400+ level nests to hammer recursion limits, while `_build_padded_attr_document()` and `_prepend_massive_padding()` generate multi-megabyte attributes. Random mutations draw from routines like `_overflow_link_href()` (format-string injection), `_insert_xml_bombs()` (entity expansion/XXE), `_aggressive_tag_corruption()` (mismatched closing tags), and `_insert_bad_values()` (huge token dictionaries) to keep payloads structurally valid but hostile.
- **JSON inputs (`JSONMutator`).** Deterministic seeds cover deep object nesting, huge numeric literals, stress-test lists, and explicit malformations (`_det_malformed_explicitly`). At runtime `_mutate_structure()` walks the parsed object graph, adding/removing keys, shuffling list elements, flipping types, and injecting Unicode edge cases before occasionally calling `_malformed_json()` to break quoting rules.
- **CSV inputs (`CSVMutator`).** Deterministic generators mutate headers, column counts, delimiters, and line endings (`_det_duplicate_header`, `_det_extra_header_100_cols`, `_det_newline_in_quoted_field`, `_det_csv_formula_in_first_data_row`). During fuzzing `_mutate_field()` swaps numeric boundaries, strips quotes, or doubles content, while the mutator randomly inserts/drops columns and appends synthesized rows to trigger parser resynchronisation bugs.
- **JPEG inputs (`JPEGMutator`).** Structured variants adjust SOF dimensions, Huffman/quantization tables, and scan headers (`_mutate_dimensions_overflow`, `_mutate_dht_payload`, `_mutate_sos_header`) or rewrite segment lengths/truncate entropy data. Random mutations pick from the same catalogue, forcing extreme image sizes, inconsistent sampling factors, or corrupted tables before optionally falling back to generic byte havoc.
- **Plaintext & raw blobs (`BaseMutator` + `OctetMutator`).** `BaseMutator` handles line-oriented seeds by substituting integer boundary values, exponentiating numbers, appending format specifiers, or XOR-flipping whole lines. When detection falls back to octet-streams, `OctetMutator` isolates non-printable regions, performs mask-based XOR sweeps, and then routes the result through `mutate_bytes()` so even mixed ASCII/binary payloads see bitflips, random insert/delete, and duplicate operations.
- **ELF inputs (`ELFMutator`).** Deterministic seeds target ELF structure directly: `_det_corrupt_ident()` flips e_ident bytes in the `\x7FELF` magic, `_det_truncate_header()` chops the file to a bare 64-byte header, `_det_entrypoint_zero()` zeros the 8-byte `e_entry` field, while `_det_empty_file()` and `_det_overflow_bytes()` exercise empty and oversized binaries. At runtime `mutate()` keeps ELF files structurally recognizable but numerically toxic by applying arithmetic tweaks to selected 16-bit header fields (offsets 16, 18, 44, 48; deltas like −1, +1, ±0x100, +0x7FFF) before chaining 1–3 rounds of generic `mutate_bytes()` havoc; non-ELF inputs bypass the structured path and go straight through `mutate_bytes()` for blind byte-level fuzzing.

Irrespective of format, every mutation passes through `BaseMutator.mutate_bytes()` at least once, ensuring we still explore the low-level input space beyond the structured edits above.

## Harness Design

The harness executes each input via the forkserver:

1. `forkserver.py` launches the target once, maps two shared-memory regions (input buffer + coverage bitmap), and waits for commands on a control pipe.
2. `fuzzer.py` writes the mutated sample into the shared-memory staging buffer and signals the forkserver, which clones the paused process, patches stdin to read from the buffer, and resumes execution.
3. Timeouts are enforced by waiting for the child pid on the status pipe; late children are sent `SIGKILL` to keep the campaign responsive.
4. Basic coverage is approximated by `forkserver_lib.c`, an `LD_PRELOAD` shim that hooks frequently used libc routines (`write`, `mmap`, `malloc`, …) and increments bytes in the shared bitmap based on the caller’s return address. When the forkserver cannot start (e.g., unsupported platform), the harness falls back to hashing `(exit_code, len(stdout), len(stderr))` as a coarse behavioural signature.

Crash outputs are deduplicated by a BLAKE2 digest built from the coverage bitmap (when present) plus truncated stdout/stderr. Each unique tuple is logged to `fuzzer_output/bad_<prog>.txt` with the culprit input, while hangs and clean exits feed back into the mutation scheduler for prioritisation.

## Capabilities

The combined system delivers:

- Deterministic and random phases that complement each other.
- Large-payload and deep-recursion generation to stress stack/heap boundaries.
- Persistent forkserver execution for high throughput.
- Crash deduplication, hang detection, and corpus management.
- Basic coverage guidance without requiring binary recompilation.

## Bugs Exercised (11 Challenge Binaries)

The fuzzer was validated against all eleven XML challenge fixtures. Each campaign recorded at least one crashing input in `fuzzer_output`, demonstrating the ability to rediscover every seeded bug.

## Limitations and Future Work

- **No PDF campaign yet.** Skeleton mutators exist in code, but we have not implemented dictionaries or deterministic strategies for those formats, nor have we validated the harness on PDF binaries. Extending beyond XML will require fresh seeds and format knowledge.
- **Naïve coverage metric.** The `LD_PRELOAD` shim only observes high-level libc entry points, so the bitmap is sparse and misses intra-function control flow. Without the forkserver we degrade to hashing exit codes and IO lengths, which is even coarser. Integrating edge coverage via QEMU or compiler instrumentation would vastly improve guidance.
- **Input minimisation absent.** Crashing payloads are stored verbatim; adding automated triage (delta debugging, line-based slicing) would reduce analyst effort.
- **Scheduling heuristics.** Strategy weights are static. Adaptive power schedules based on recent coverage wins could further accelerate discovery.
- **Resource awareness.** The fuzzer currently trims inputs at 1 MB but does not monitor RSS or file descriptor pressure. Hardening these limits would stabilise long campaigns.

## Something Awesome: Forkserver 

We implemented a custom forkserver (`forkserver.py`) to earn the bonus marks. The controller maps the target once, shares SHM metadata for status codes, and services run requests by issuing `fork()` calls and piping mutated stdin. This mirrors AFL’s design, reducing per-test start-up from tens of milliseconds to microseconds and making timeouts more precise. The same channel also carries basic coverage observations, keeping overhead low enough to run within the provided Docker container.
